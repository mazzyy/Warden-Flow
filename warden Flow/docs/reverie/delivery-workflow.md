# Warden Flow — the DELIVER workflow

**Reverie Hacks 2026 · ML Prompt Engineering track**

Warden Flow is an AI DevOps engineer with two workflows built on one structured-prompting engine. The **OPERATE** workflow (documented in `node-documentation.md`) fixes a broken service. The **DELIVER** workflow, below, ships one — it takes a repository and produces the artifacts to run it in production, each generated by a narrowly-scoped node, each returning a typed object, with a human gate before anything is applied.

```
a repo → Assess → Containerize → Pipeline → Deploy-Plan → [Human review] → Verify → shipped
```

The same three prompt-engineering principles run through it: **one job per node**, **typed output enforced** (Pydantic `output_schema`), and **structured handoffs** (each node consumes the previous node's typed result, not the raw repo).

---

## The nodes

| # | Node | LLM query | Typed output | Reads |
|---|------|-----------|--------------|-------|
| 1 | **Assess** | What is this repo — language, entrypoint, ports, deps? | `RepoProfile` | the local source dir |
| 2 | **Containerize** | Write a production Dockerfile | `Dockerfile` | source + profile |
| 3 | **Pipeline** | Write CI/CD: build→test→scan→push→deploy | `Pipeline` | profile + base image |
| 4 | **Deploy-Plan** | Write manifests + rollout/rollback | `DeployPlan` | profile + Dockerfile |
| ★ | **Human Review** | *(no LLM)* approve the artifacts as a PR | merge/reject | — |
| 5 | **Verify** | Validate every artifact against a checklist | `VerifyReport` | everything generated |

**What makes each node prompt-engineering and not a template:** the constraints are *in the prompt*, and each defends a specific failure.

- **Assess** is told: "if a fact is not in the files you read, say so rather than fill it in." *Defends against* a containerizer trusting a guessed port or entrypoint. (On a live gpt‑5.6 run with an empty source dir, the node correctly returned "unknown" instead of inventing — the prompt working as designed.)
- **Containerize** must enforce, and record: pinned base (never `:latest`), multi-stage, non-root user, no secret baked into a layer, minimal runtime, explicit `EXPOSE`/`HEALTHCHECK`. *Defends against* the single most common failure — an image that builds but runs as root from an unpinned base.
- **Pipeline** must gate push/deploy on `main`, add a vulnerability **scan** stage that fails on high/critical, reference secrets as `${{ secrets.NAME }}` (never hardcode or echo them), and request least-privilege permissions. *Defends against* a pipeline that ships an unscanned image or leaks a credential.
- **Deploy-Plan** must set resource requests *and* limits, liveness/readiness probes, a non-root `securityContext`, and an immutable image tag; and state the rollback in one line. *Defends against* an unbounded pod that takes down a node, and a rollout with no way back.
- **Verify** is the gate before the human: it re-checks all of the above and sets `passed=false` on any critical miss. *Defends against* trusting the generators.

## The proof — `warden bench-deliver`

The track's core question is whether structured prompting beats a single prompt. For delivery, the answer is stark and **computed from the Dockerfile itself**, not asserted:

```
SCOREBOARD  (same service, same model — only the structure differs)
  best-practice check           single prompt   warden flow
  pinned base (no :latest)      FAIL            pass
  multi-stage build             FAIL            pass
  runs as non-root              FAIL            pass
  has HEALTHCHECK               FAIL            pass
  no secret baked in ENV        FAIL            pass

  score  single prompt 0/5   ·   warden flow 5/5
```

A single "here's my app, write a Dockerfile" prompt returns something that builds and is unsafe — `FROM python:latest`, root user, the whole context copied, a token baked into an `ENV`. The staged workflow, given the same app and the same model, returns a pinned, multi-stage, non-root image with a healthcheck. Both build; only one is safe to ship. Run it:

```bash
make bench-deliver        # offline, free, deterministic
make bench-deliver-live   # same, on real models
```

## Model selection — including Azure GPT‑5.6

Every node's model is declared in its manifest and is swappable without touching orchestration. A single resolver routes the node to the right backend:

- **Gemini** (native) — the default.
- **Azure OpenAI GPT‑5.6**, **OpenAI**, or **Anthropic** — via `DELIVER_MODEL=azure/<deployment>` (or `openai/…`, `anthropic/…`), through LiteLLM.

This was verified live: the DELIVER nodes ran on **Azure GPT‑5.6**, and the typed schemas (RepoProfile, Dockerfile) came through cleanly via Azure's Responses API — the same governance, budgets, and structured output as Gemini, on a different provider.

```bash
# in .env
DELIVER_MODEL=azure/gpt-5.6-sol
AZURE_API_KEY=…
AZURE_API_BASE=https://<resource>.openai.azure.com/
AZURE_API_VERSION=2024-12-01-preview

make deliver-live
```

## How it reuses the engine

Nothing about the runtime changed to add delivery: the DELIVER nodes go through the same `run_agent` (budgets, audit, retries), the same policy proxy, and the same manifest/`output_schema` machinery as the incident fleet. The delivery nodes live in `manifests/delivery/` so the incident fleet stays exactly four agents and every safety test still passes. What's new is *what the nodes reason about* — which is precisely what makes DELIVER a different job from Warden, not a re-skin.
